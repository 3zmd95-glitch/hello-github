## Search before building

TikTok's maintained [Business API SDK](https://github.com/tiktok/tiktok-business-api-sdk) is MIT licensed. Its [official OpenAPI schema](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/yml_files/discovery_trending_list.yml) confirms `HASHTAG`, the twelve category mappings already in the app, and `SPECIAL_EFFECTS`/`PHOTOGRAPHY`. The period enums are `1DAY`, `7DAY`, `30DAY` and `120DAY`, with `US`, `ALL`, and `7DAY` defaults. Country is typed as a string; that is not confirmation of Saudi coverage. The [official JavaScript adapter](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/js_sdk/src/api/CreativeManagementApi.js) sends the ordinary query and an Access-Token header. No free-text search or request-signature field appears in this operation.

The current public SDK tree did not establish a `video_list` contract. Direct detailed authorization views remained JavaScript shells, so the exact current permission identifier and account-specific entitlement are unverified. The existing code's comments are not proof of provider support. A successful hashtag response establishes only that one request, not related-video access, useful editing candidates, a private personalized feed, audio reuse or trend growth. Independent review of the official response schema found that the provider's `code` field is optional and nullable, described as appearing on errors. A strictly valid successful list must therefore remain acceptable when the provider omits that field; no success code is invented in the receipt.

Reuse the existing encrypted advertiser integration and bounded HTTP approach; no new SDK dependency, connector or permission is required to attempt a read under an existing grant. This is a narrow capability check before expanding acquisition. Do not extract native browser cookies, read token files, initiate OAuth automatically or manufacture an advertiser ID.

## Implementation boundary

The client explicitly checks `/tiktokads/status` through its existing Scout connection. Missing stored connection or zero advertisers stops there. A connected state may then invoke the new authenticated `POST /categories/:id/native/tt/probe`, for a known built-in category only. The new Worker route is not assumed deployed merely because the frontend is updated.

The probe attempts at most one `discovery/trending_list` read using the existing advertiser grant, a fixed documented baseline of `HASHTAG / US / 7DAY`, and that category's documented industry. It performs no paid/indexed search, video acquisition, public-caption read, model call, pagination, retry, OAuth or scheduled work. Missing grant performs no provider request. The response must distinguish accepted-empty from malformed data and connection/auth/permission/rate-limit/network/timeout failures. Only bounded nonsecret status, stage, request count, observation time, fixed query context and hashtag count may be returned; no raw provider body, message, token, advertiser identifier or candidate is exposed. The browser control also distinguishes a missing backend route from a provider refusal, including responses with an empty error body. Cancelling or navigating away must prevent a stale result or second-stage probe from appearing under a different category.

After a valid accepted response, a separate bounded acquisition experiment must establish a documented/current related-video contract and useful exact-post results. Current candidate and source-evidence rules still apply. Do not use an accepted chart as a shortcut around relevance, publication-date, engagement or audiovisual checks.
