# An editor's discovery feed — 9 October 2026

## Problem and acceptance

The owner wants useful editing inspiration and lessons across categories, with current popular examples, not unrelated category search hits or five-like videos presented as trends. Audits in [20](20-discover-inspiration.md), [21](21-discover-quality-audit.md), and [22](22-edit-formats.md) showed that keyword relevance, lifetime popularity, and actual editing quality are different questions. A song's cumulative uses also do not establish adoption of a particular visual recipe.

The near-term implementation combines a bounded, reusable candidate library, conservative source-aware ranking, and explicit local preferences. It does not claim to reproduce Instagram's or TikTok's private recommendation models. More candidates and a ranking model cannot compensate for inaccessible or missing source evidence; sparse results must remain honest.

## Primary-source access research

Sources reviewed on 9 October 2026; availability for this application's existing authorization is separate from a platform documenting an API.

- [YouTube search.list](https://developers.google.com/youtube/v3/docs/search/list) supports publication bounds and different ordering choices. Its documentation warns that some non-relevance order/date combinations can produce incomplete results. Use bounded discovery to find relevant creators, then creator upload playlists for repeatable coverage and [videos.list](https://developers.google.com/youtube/v3/docs/videos/list) for current public statistics. Authorized `myRating=like` offers a possible future source of explicitly liked videos; it is not access to the user's Home feed.
- The maintained [TikTok Business API SDK](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/python_sdk/docs/CreativeManagementApi.md) documents creative discovery/detail and trending-list operations. Their availability and response fields depend on the approved app. Hashtag charts are not a personal For You feed or proof that each related video has popular editing. The current repository's category adapter needs actual post metadata before making engagement claims.
- [TikTok Display API](https://developers.tiktok.com/doc/display-api-overview/) provides an authorized creator's uploads and metadata. It is not a replacement for public video search or For You recommendations. [Research API eligibility and data freshness](https://developers.tiktok.com/doc/research-api-faq/) make it unsuitable to assume as this commercial application's immediate trend backend: access is restricted, and research search/statistics are not guaranteed live.
- [TikTok Data Portability](https://developers.tiktok.com/products/data-portability-api/) is an optional future route to authorized personal data for eligible users and approved apps. Its regional availability must be checked; do not assume it applies to this Saudi owner. No history import or implicit watch tracking was added.
- Meta's Audio API reference could not be read reliably during this research. Do not conclude that audio discovery is impossible. The maintained [Postiz Instagram provider](https://github.com/gitroomhq/postiz-app/blob/main/libraries/nestjs-libraries/src/integrations/social/instagram.provider.ts) implements Graph `/ig_audio` through its Facebook Login path, returning audio metadata and allowing an empty search query for audio discovery. That is practical evidence to investigate, not proof that this application's Instagram Login credentials support it. Audio metadata alone does not list matching visual formats or measure their growth. The [official generated Instagram user SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/iguser.py) exposes business discovery; verify app permissions and account coverage before connecting that route.

No browser-token extraction, private-feed scraping, new provider or credentials import was introduced. A later explicitly authorized, capped live retrieval comparison spent four Tavily pay-as-you-go credits ($0.032); pay-as-you-go and automatic upgrades were turned off afterward. See the [9 October handover](../handovers/discover-editor-feed-2026-10-09.md) for the trial and remaining access limits. Bounded public-source reads may be unavailable; a failed lookup must not manufacture statistics or replace the publication date with the lookup time.

The existing Instagram integration uses Instagram Login through `graph.instagram.com`. Meta's [official Facebook Login collection](https://www.postman.com/meta/instagram/folder/u4g5a2a/instagram-api-with-facebook-login) describes business discovery and hashtag access through the Facebook Login/linked-Page path. That documentation does not establish that the current connection has those permissions. No alternate login integration was added in this pass. The unresolved automatic-discovery gap is native source coverage and audiovisual inspection, not evidence that buying more general web searches will solve it.

## Open-source choices

- [Gorse](https://github.com/gorse-io/gorse) provides recommendation infrastructure around users, items, feedback and similarity. It requires a separate service and data stores. Defer it: the current bottleneck is trustworthy candidate coverage and a small personal interaction set, while the existing static-export app and Worker already support local deterministic ranking. Gorse supplies no Instagram/TikTok data access.
- [Transformers.js](https://github.com/huggingface/transformers.js) can run text/image embeddings locally or in the browser. Defer model downloads and runtime cost until accessible media, Arabic/English quality, and relevance benchmarks justify them. Embedding similarity is not evidence of popularity or a shared temporal editing recipe.
- [Vowpal Wabbit contextual bandits](https://vowpalwabbit.org/docs/vowpal_wabbit/python/latest/tutorials/python_Contextual_bandits_and_Vowpal_Wabbit.html) are a later option once deliberate actions generate enough reward observations. Adding a learner before useful candidates and honest feedback would optimize the wrong inputs.

Reuse the repository's existing Zustand persistence, Zod validation and installed [idb-keyval](https://github.com/jakearchibald/idb-keyval). Its custom stores and atomic `update` provide asynchronous candidate persistence without introducing a server or dependency. [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) fits a structured local corpus better than repeatedly serializing it into the small synchronous progress save. [fflate](https://github.com/101arrowz/fflate) was considered and deferred: compression alone does not fix the old item cap or separate candidate writes from user progress, and adds decoding/boundary work. No dependency was installed and no third-party implementation was copied.

## Local library and feedback contract

`lib/discoverFeed.ts` keeps whitelisted raw `DiscoverItem` fields, source evidence, the category, and `obtainedAt`. Canonical post URLs deduplicate inside each category. Direct source evidence wins over a later indexed excerpt; older observations cannot overwrite newer source data. Enriching a post preserves its original receipt time in that category, and identical payloads cause no store update. An explicit newer unavailable source is retained so ranking can suppress a broken post. Receipt time is never a publication date, metric observation, or proof of a new trend.

The durable library retains at most 100 candidates per category, 3,000 overall, and 6,291,456 serialized characters (roughly 12 MiB of UTF-16 text). This accommodates 100 candidates in all 12 built-in categories plus custom categories, independently of the progress save. The prior 500-item/600,000-character shared budget lost useful qualified examples during a 12-category tour; stricter ranking alone did not solve that storage loss. Retention prioritizes genuine category lessons and creative examples with meaningful engagement before weak recent arrivals. Creative projects described in prose can qualify for this cache priority; an edit hashtag on an ordinary plot clip cannot. Within equal quality, platform and lesson/example lanes alternate. At a safety cap, selection rounds alternate categories, including when verbose captions hit the text limit first. Full source payloads are preserved. Unchanged payloads retain their object identity and cached size; below the caps, repeated accumulation avoids whole-corpus sanitization and quality rescoring. Cache priority never grants displayed Popular admission. Existing explicit retrieval and refresh budgets remain unchanged.

An authentic caption that independently establishes a known category's creative relevance can supersede stale indexed off-topic/category flags. Missing captions, a different category, promotional exclusions and explicit source unavailability cannot use this exception. Both cache retention and ranking apply this rule. `lib/discoverMetadata.ts` reuses only exact category/text analysis in a bounded ephemeral cache (500 entries and 1,000,000 key characters). Dates, metrics, preferences and final scores always recompute; changed captions are reanalyzed. A local 500-candidate, 12-category benchmark with cloned inputs and roughly 1.1k-character captions measured 168–201ms for a cold mixed-feed pass and 23–27ms for repeated warm passes. This synthetic timing is not a guarantee for every device or caption size.

Live review also found real source captions containing unfinished alternate-caption drafts: a list of polished technique claims followed by “Or, if it's specifically for a car edit:” and a `KEYWORD` block. Those marked draft paragraphs cannot establish craft or teaching evidence. A separate descriptive title or real instructional passage remains usable; legitimate AI workflows, memes, hashtags and tutorials quoting a prompt are not categorically rejected. Analysis preserves the title/description boundary, including older official YouTube payloads that joined an exact native title with a space. Source captions and engagement counts remain intact for display; this is a conservative metadata integrity check, not a claim that the video was watched.

Preferences are deliberate `more`, `less`, and `hide-creator` actions. Item preferences are scoped to canonical post and category; creator hides span categories on the same platform. Unknown creators are not grouped together. A `clear` action removes the related preference and creator hide; an Undo token restores the prior affected records only if they have not since changed. Unrelated later choices are preserved. At most 500 effective preferences persist. Clicks and opening videos are not converted into watched or liked signals.

Deliberately imported links carry a category-scoped candidate `origin: "manual"`, separate from the post and its source evidence. This retention priority prevents a sparse personal reference from being immediately evicted by 100 automatically retrieved candidates; it remains within all library limits. Native enrichment and exports preserve origin, while another category's automatic copy does not inherit it. This provenance survives clearing preferences because the import still happened. The separate explicit Keep/More choice controls personal feed admission; manual origin alone supplies no technique, category, availability or popularity claim. A confirmed unavailable source still remains excluded from display.

Feedback and progress remain in the existing localStorage save. `lib/discoverLibrary.ts` persists candidates separately in the `3z-prod-discover` IndexedDB database using an atomic source-aware merge. Existing localStorage candidates migrate only after a confirmed durable write, then the localStorage copy is removed. Startup merges candidates added while reading and gates initial category requests until storage settles, so a delayed database cannot cause an unnecessary paid search. Reads and writes have five-second bounds; timed-out native writes abort their transaction. If storage is unavailable, progress keeps a bounded 500-item/600,000-character candidate fallback and the store reports `unavailable`; the full current in-memory corpus remains exportable.

Exports include the full hydrated corpus. Import/reset use a new opaque epoch, fence old reads and queued writes, and persist replacement intent until it succeeds; an ordinary stale-tab write cannot restore an older epoch. Cross-tab epoch changes discard the prior in-memory corpus before adopting the new durable contents. Export is disabled while hydration is pending. Older backups default to empty arrays, and malformed entries are skipped. This database contains candidate metadata only, with no account credentials. Browser storage can still be denied or cleared; exports remain the portable backup.

`savedDiscoverInterests` derives a weaker, ephemeral preference from existing saved references and their `saved`, `trying`, or `tried` stages. Unsaving removes that signal. Notes are not mined into technique claims. Exact saved matches receive a small ranking boost; related-creator/technique affinity requires that the saved post is present in the current candidate pool with valid category and craft evidence. Saving alone never qualifies a weak item for Inspiration or Popular, and explicit less/hide actions take precedence. Followed formats are not converted into generic technique preferences: shared words such as clone do not establish the same audio/visual recipe.

## Cached For You landing

`lib/discoverForYou.ts` supplies Browse with a mixed feed from the existing local library. It runs the same Inspiration, Popular, Learning or Explore policy inside each original category first, preserving subject checks and category-specific feedback. It then deduplicates canonical posts and gives different available categories and creators a place before repeats. A small capped category-order preference comes only from positive feedback or saved/practiced posts present among that category's qualified candidates. A disliked example is not interpreted as disliking the entire category.

Each row retains its category and source/date evidence for display and feedback. Newer authentic source observations are shared across category duplicates before ranking: an unavailable post or corrected count must not leak through an older copy. The latest explicit Less action for a post suppresses its duplicates in this mixed feed; a newer More can reverse that suppression. Category screens retain their existing scoped behavior. Default output is at most 30 items, with the distinct qualified count available separately for pagination and shortage reporting.

This helper performs no search, source lookup, storage write, private-feed access or inferred watch tracking. A new user with an empty library gets an honest empty state and category choices. Returning users see their previously retrieved examples and deliberate preferences; the cache is not described as a live platform-wide feed or a rising-trend measurement.

## Retrieval and source grounding follow-up

The three explicit category-expansion rounds now use genuinely different creative queries. Previously the first two repeated queries already used by the initial category planner, while the last merely appended calendar text. Expansion now passes the existing supported `timeRange: "month"` field through the normal cache-aware search path, with exact English queries and at most one search request per selected platform per click. No extra provider or automatic retrieval was added. A fresh date filter can improve candidate supply but does not establish trend adoption, and indexed dates still need source validation. The [maintained Tavily client](https://github.com/tavily-ai/tavily-python/blob/master/tavily/tavily.py) and repository Worker already support this time-range parameter.

`lib/youtubeEvidence.ts` optionally reuses a YouTube key already configured in dashboard settings. One read-only official `videos.list` request grounds up to 50 previously retrieved video IDs in actual title, description, author/channel, publication date, views and likes. It uses the existing API URL helper, a six-second timeout, a bounded response, and a memory-only key-scoped cache (six hours for source metadata, 15 minutes for omitted IDs). It never adds the key to candidate records or exports. Absent keys, API errors and omitted IDs leave availability unknown; only an explicit private/deleted/rejected response records unavailable. This is metadata verification, not another video search or audiovisual inspection. The [official endpoint documentation](https://developers.google.com/youtube/v3/docs/videos/list) describes the snippet/statistics/status parts and one-unit request cost.

For previously trimmed candidates, existing `peekDiscover(config, exactRequest)` can recover a still-valid cached complete answer without any provider request. Its request key includes category, query and filters, so callers must recreate the same request. The session memory cache can contain more categories than the persistent cache, which retains at most eight answers for 24 hours. Recovery must report misses honestly and must not silently replace a cache miss with a paid search.

## Evidence and validation limits

Popular admission needs category/craft relevance, a plausible recent publication date, a sufficiently recent source observation and a stated engagement floor. These floors are product screening choices, not universal definitions of popularity. Likes are not converted into invented views. A low-engagement tutorial can still be useful in learning without being labeled popular. A rising claim needs at least two comparable dated observations; a format-adoption claim needs independent creators and actual matching visual/audio evidence.

Pure and store tests cover URL/creator identity, category isolation, evidence preservation, stale-result protection, unavailable-source updates, bounded storage, scoped Undo, legacy backups and no-op repeated accumulation. A 12-category verbose-payload regression retains qualified examples and lessons after repeated low-like source updates without truncating captions; another retains all 24 recent qualified examples per category across a tour and rehydration. Persistence tests cover confirmed migration/localStorage omission, write-failure fallback, startup mutations, delayed reads, import/reset races, stale-tab epochs, and the production adapter's atomic update and abort path. A real Chrome tour, reload and repeat tour preserved all 248 exported candidates across all 12 categories; their compact JSON occupied 635,873 characters, exceeding the old 600,000-character cap. Eleven categories had identical visible Explore counts. Football lost one visible TikTok result through source/ranking reevaluation, while both records remained in the exported library. The actual downloaded backup was checked.

The capped Instagram Anime comparison returned no posts for the monthly query. The evergreen query returned 17 candidates, 16 broader matches, zero Inspiration and four Learning results. One Learning result, [edie_edit's CapCut lesson](https://www.instagram.com/reel/DaEoPMBMxdD/), was actually played: around 19–27 seconds it demonstrated text duplication on a CapCut timeline. Its reported 27 June date and 818 likes make it an older useful lesson, not a current trend. The other three Learning clips were not thereby visually verified. Live review also found a full thriller movie admitted because its title mentioned the desert; full-feature-upload title markers are now excluded while genuine short films and movie-editing tutorials remain eligible.

YouTube grounding tests cover exact ID binding, count/date validation, missing-ID uncertainty, memory caching, the 50-ID cap, cancellation and failures. These validate application behavior, not whether every creator's clip contains a cool edit. Category acceptance still requires inspecting representative actual videos; inaccessible posts and unverified audiovisual properties must be reported as such.
